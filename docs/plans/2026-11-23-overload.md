# API overload protection

## Acceptance targets

| Offered load | Required result |
|---:|---|
| 160 req/s | Readiness ≥ 98%, overall p95 ≤ 500 ms, request errors ≤ 1%, and at least 95% of scheduled requests issued |
| 240 req/s | Readiness ≥ 98%. Report throughput, p95, errors, and issuance against the session baseline. |
| 640 req/s | Sustain at least 160 successful req/s across the round as the proposed goodput floor. Shed requests return `503` with `Retry-After`, with a proposed rejection p95 ≤ 200 ms. Liveness stays at 100% and recovery takes under 5 seconds. |
| 960 req/s | Report the same measurements as a stress result. |

Report generator CPU as a percentage of one logical core, the scheduled and issued counts, and any pacing or CPU limit at every level. Flag the 640 req/s result as generator-limited if it issues under 95% of the schedule. Report successful throughput and timed-out requests alongside deliberate `503` responses. Measure recovery from the end of scheduled load to the first of two consecutive successful checks of liveness, readiness, and an authenticated read, using 250 ms sampling after the load window. Preserve the existing workload and probe cadence during the measured window.

Liveness returns a static `200`. All health routes bypass the rate limiter and admission limit. Liveness performs zero PostgreSQL or Redis calls. Readiness serves a timed background dependency snapshot and bases its status on PostgreSQL, the Redis cache, and the Celery broker.

## Baseline for comparison

Use the verified 2026-11-23 session baseline from `ec5e291`. The isolated fixture started with 5,000 users, 20,000 categories, and 320,000 seeded transactions. The two-minute rounds ran on the Ryzen 7 7840HS WSL2 host with four logical CPUs and 5.8 GiB RAM, two Granian workers, two Celery worker processes, PostgreSQL 16.16, and Redis 7.4.12. The open-loop workload used 87% reads and reports (44% transaction lists and 43% monthly summaries), 12% transaction writes, and 1% logins. Each health route received one probe per second with a one-second timeout. Workload requests had a three-second timeout.

## Server and database configuration

- Granian 2.7.5 applies `--backpressure` (`GRANIAN_BACKPRESSURE`) per worker at connection acceptance. The default is `backlog / workers`, nominally 512 with the default backlog of 1,024 and two workers. Connections queue when the threshold is reached. Because this happens before HTTP routing, the setting alone cannot send a `503` with `Retry-After` or exempt probe traffic. Retain the two-worker baseline and use Granian's setting as a transport guard with headroom for probes. Use app-level admission only for the response and exemption behavior the transport setting cannot provide. Verify new and reused connections in the admission test. [Granian 2.7.5 backpressure](https://github.com/emmett-framework/granian/blob/v2.7.5/README.md#backpressure)
- The current API pool has five persistent and five overflow connections per worker, with a 30-second checkout timeout. Two API workers can open up to 20 connections, and two dedicated readiness connections would bring the API maximum to 22. The capacity database reports `max_connections=100`, `reserved_connections=0`, and `superuser_reserved_connections=3`. Start with pool size and overflow unchanged. Keep API replicas, worker processes, Celery pools, migrations, and other clients within the 97 ordinary slots on this database, with headroom for maintenance. Check the connection budget independently for production. [PostgreSQL 16 connection settings](https://www.postgresql.org/docs/16/runtime-config-connection.html) · [SQLAlchemy 2.0 connection pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html)
